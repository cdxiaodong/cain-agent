# Benchmark 评测方案 · cain-agent

> 落地 DESIGN.md §3.5 评测体系。靶场只做工程回归,实战数据才是能力证明——两层设计缺一不可。
> 版本:v1 · 2026-08-05(随本地回归靶场 compose 落地)。

## 设计原则

1. **工程底线 ≠ 能力证明**:靶场回归保证不退化,实战战果证明能打真目标;两者数据分开呈现,不得用靶场检出率冒充实战能力。
2. **指标口径前置**:在跑任何评测前,先把「什么算检出、什么算误报」定义死,否则不同版本的数据不可比。
3. **只读与授权为先**:所有评测在已授权靶标上运行;实战层严禁触碰无授权目标。
4. **可重复**:靶场用 compose 固定版本,每轮评测环境一致;实战层用授权任务快照。

---

## 第一层 · 靶场回归(工程底线)

### 目标

每个版本回归一遍:检出率 / 误报率 / 耗时 / token 成本四指标,作为工程基线,防止重构时能力退化。README 放 badge 趋势图。

### 靶标体系

| 靶标 | 类型 | 覆盖技能 | 说明 |
|---|---|---|---|
| **本地 compose 靶场** | 自托管 | SQLi / XSS / SSRF 探测 | `bench/docker-compose.yml`,Juice Shop + DVWA,127.0.0.1 绑定,本地授权回归用 |
| **XBOW 靶场** | 公开 SWE-bench 风格 | 综合漏洞发现 | OWASP 主导的 Web 漏洞自动发现基准,行业可比;每版跑一轮对齐同类项目 |

### 本地 compose 靶场用法

```bash
cd bench
docker-compose up -d
# Juice Shop:http://127.0.0.1:3000 (开箱即用)
# DVWA:http://127.0.0.1:8080 (首次访问 /setup.php 点击 Setup 初始化)
docker-compose down -v   # 用完即清,数据不落宿主
```

> 端口仅绑 `127.0.0.1`,不暴露到局域网;靶标是故意带漏洞的训练靶,不得接入生产网络。

### 四指标口径定义

> 口径必须可机械判定,不靠人工感觉。

- **检出率(detection rate)** = `TP / (TP + FN)`。
  - **检出(TP,True Positive)**:Agent 输出的 finding 中,经靶标已知漏洞清单(ground truth)比对,issue_type 与漏洞点(参数/端点)匹配且状态为 `confirmed`。同一漏洞多 finding 只计一次(指纹去重,见 `findings.dedup`)。
  - **漏报(FN,False Negative)**:ground truth 中存在、但 Agent 未输出对应 confirmed finding 的漏洞。
- **误报率(false positive rate)** = `FP / (FP + TN)`。
  - **误报(FP,False Positive)**:Agent 输出的 finding 中,无法在 ground truth 找到匹配、且经校验后状态为 `false_positive` 的条目。仅状态未定(`validation_inconclusive` / `validation_system_error`)不计入误报,单独统计为「待校验」。
  - **真负(TN,True Negative)**:Agent 正确未报告不存在的漏洞——按靶标无漏洞的端点数减去误报计。
- **耗时(time)**:单轮评测从首个请求到产出最终报告的墙钟时间(秒),不含模型 API 排队等待;单独记录 token 排队时长作为噪声标注。
- **token 成本(token cost)**:单轮评测消耗的输入+输出 token 总数,按模型计费口径统计;预算熔断触顶时标注「被预算截断」。

> ground truth 由靶标官方文档 + 人工标注的漏洞清单维护,作为仓库 `bench/ground-truth/` 的只读基准(后续任务落地)。

### 报告输出

每轮评测产出:

- `bench/results/<date>_<commit>/`:逐 finding 的判定(TP/FP/FN + 去重指纹)、四指标汇总、token 与耗时。
- README badge:检出率 / 误报率 / 耗时 / token 的版本趋势。

## 第二层 · 实战验证(能力证明)

### 目标

在合法授权的真实目标上验证能力,建立「实战战果」页:确认漏洞数、厂商致谢、CVE/CNVD 编号(脱敏展示)。这是与同类项目的核心差异叙事。

### 合法授权渠道(仅限下列,缺一不可:授权 + 目标在 scope)

| 渠道 | 类型 | 授权证据形态 |
|---|---|---|
| **漏洞盒子 / 补天** | SRC 平台 | 平台任务页截图 + 任务 ID |
| **VDP 项目(厂商漏洞披露计划)** | 厂商直投 | VDP 政策页 URL + 授权范围条款截图 |
| **自有测试资产** | 自有环境 | 资产所有权证明(云账号归属截图等) |
| **授权客户环境** | 商业项目 | 签署的渗透测试授权书(合同/SoW) |

### 授权证据留存要求(红线,违反即打回)

1. **每个实战目标必须有书面授权**:授权书 / 平台任务截图 / VDP 政策页,存档于项目内部证据库(不入仓库,避免泄露目标信息)。
2. **scope 边界由配置强制**:`scope.yaml` `in_scope` 仅含授权范围;ScopeGuardHook 在 PreToolUse 拦截越界,不靠 Agent 自律。
3. **披露即脱敏**:README、报告、对外文章中,目标名称/资产/IP/漏洞细节须脱敏;厂商致谢需经厂商同意后方可公开。
4. **凭证只哈希不落明文**:实战中发现的 AK/SK/Token,证据只存哈希与类型。
5. **只读原则**:核心功能 ReadOnly 凭证即可验证;写操作工具不注册,不在目标上做破坏性/持久化测试。

### 实战层指标

实战层**不追求**像靶场那样的检出率百分比(真实目标 ground truth 未知),而记录:

- 确认漏洞数(经厂商/平台确认):按严重度分布。
- 厂商致谢数 / CVE/CNVD 编号数。
- 平均单目标确认耗时与 token 成本(供优化,不对外排名)。

> 禁止用「疑似漏洞」当战果;只计 `confirmed` 状态且经外部确认的发现。

## 评测节奏

- **每个版本**:本地 compose 靶场跑一轮四指标,趋势入 README badge。
- **每个里程碑**:XBOW 靶场跑一轮,对齐同类项目行业可比数据。
- **持续**:实战战果按确认节奏更新(脱敏),作为能力背书。

## 不做(本阶段)

- 不实现评测执行脚本(引擎跑靶场是后续任务,本方案只定口径与靶标配置)。
- 不启动真实扫描、不触网。
- 不对外发布未经厂商同意的实战细节。
