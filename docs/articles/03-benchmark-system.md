---

> 本文只讨论公开基准和自有合成靶场中的防御性评测，不包含真实目标、真实凭证或未公开漏洞细节。Cain 仅供获得书面授权的安全测试使用。

## 一、为什么 AI 渗透 Agent 更需要 Benchmark

传统扫描器的输出虽然也会误报，但规则、请求和匹配条件通常可以回溯。AI Agent 多了一层概率性：它会规划路径、选择工具、解释响应，再把零散证据组织成漏洞结论。任何一步都可能产生幻觉。

一个超时可能被解释成 SSRF 成功，一个普通错误页可能被描述成 SQL 注入回显，一段配置文本也可能被模型补全成并不存在的权限链。如果团队只统计“报告了多少高危漏洞”，模型越敢下结论，成绩反而越好。这样的榜单奖励的是表达自信，不是检测能力。

所以，评测首先要回答的不是“Agent 看起来聪明吗”，而是四个可机械判定的问题：它找到了多少已知漏洞，制造了多少误报，完成一轮用了多久，又消耗了多少 token。更重要的是，每个数字必须能追溯到固定靶场、ground truth、运行配置和逐条 Finding 判定。

这也是 Cain 将 Benchmark 视为工程回归而非宣传素材的原因。没有 ground truth 的真实项目可以证明实战价值，却无法计算完整检出率；有 ground truth 的靶场适合比较版本，却不能冒充真实世界战果。两类数据必须分开。

## 二、双重验证：XBOW 与 vuln-tf 各自解决什么问题

只用一种靶场容易形成偏科。Cain 的方案由公开 Web 基准 XBOW 和自建云误配置靶场 vuln-tf 组成，两者共享指标口径，但承担不同职责。

### 2.1 XBOW：获得行业可比性

XBOW 提供公开的 Web 漏洞场景和已知答案。固定场景版本后，Cain 对每个目标执行同一套 recon、test、report 流程，再把 confirmed Finding 与 ground truth 按漏洞类型、端点和参数匹配。公开基准的价值在于可复核：其他工具能够在同一数据集上运行，结果不依赖 Cain 自己设计的题目。

XBOW 主要回答“通用 Web 漏洞发现能力如何”。它能暴露漏报、重复 Finding、错误归因和超时等问题，但不能覆盖国产云 IAM、对象存储权限等平台差异。

### 2.2 vuln-tf：验证云配置检测

自建 vulnerable-terraform 场景用于补齐云侧能力。每个场景同时放置故意错误的靶标和最小权限的对照项。例如，公开读的对象存储桶应被检出，对照私有桶不应被报成暴露；过度授权的 RAM 用户应命中预期规则，对照只读用户应保持零命中。

ground truth 不藏在人的记忆里，而由 Terraform 输出和静态测试明确记录。CI 只校验配置结构，绝不执行 `terraform apply`，也不接触云凭证。需要动态验证时，只能由操作者在自有测试账号中手工部署、当天销毁，并保存脱敏结果。

双靶场形成互补：XBOW 提供外部可比的 Web 基线，vuln-tf 提供云平台差异化回归。前者防止“只会做自己的题”，后者防止公开基准覆盖不到产品真正要解决的场景。

## 三、四指标：先固定口径，再讨论分数

Cain 每轮版本回归固定记录四项核心指标。

| 指标 | 计算或记录方式 | 它揭示的问题 |
|---|---|---|
| 检出率 | `TP / (TP + FN)` | 已知漏洞中有多少被确认发现 |
| 误报率 | `FP / (FP + TN)` | 无漏洞对照项中有多少被错误报告 |
| 耗时 | 首个请求到最终报告的墙钟秒数 | Agent 是否适合持续回归和实际交付 |
| token 成本 | 单轮输入与输出 token 总和 | 能力提升是否以不可控成本换取 |

TP 不是“模型说存在”。一条 Finding 必须与 ground truth 的漏洞类型和位置匹配，并经独立验证会话判定为 `confirmed`；同一漏洞的重复 Finding 先按指纹去重。ground truth 中存在但没有 confirmed Finding 的项目记为 FN。

FP 也需要明确边界：Finding 无法匹配 ground truth，且验证状态为 `false_positive`，才进入误报统计。`validation_inconclusive` 和 `validation_system_error` 单独报告，不能偷偷归入正确结果，也不能简单算成误报。TN 则来自明确设置的无漏洞端点或安全对照资源。

耗时记录端到端墙钟时间，同时标注模型服务排队等外部噪声。token 按模型分别记录输入和输出，并汇总为单轮成本；若预算熔断触发，报告必须标记“被预算截断”。这样可以区分“更会找”与“只是跑得更久、花得更多”。

Precision 和 F1 可以作为派生指标展示，但不替代上述四项原始口径。原始计数 TP、FP、FN、TN 也必须随报告保存，否则一个百分比无法接受审计。

## 四、Benchmark 框架如何自动跑分

评测框架的核心不是一个神秘综合分，而是一条确定的数据管线：加载套件清单，校验授权与 scope，逐场景启动隔离运行，收集 Finding，交给独立验证会话复核，与 ground truth 对齐，最后聚合四指标。

```text
suite manifest
  -> isolated run
  -> findings + usage + duration
  -> independent validation
  -> ground-truth matching and dedup
  -> TP/FP/FN/TN + time + token report
```

概念上的 `BenchmarkExecutor` 只负责编排，不自行判断漏洞真假：

```python
class BenchmarkExecutor:
    def run(self, suite):
        runs = [self.run_isolated(case) for case in suite.cases]
        validated = self.validator.validate(runs)
        labels = self.matcher.compare(validated, suite.ground_truth)
        return self.metrics.aggregate(labels, runs)
```

自动化跑分还必须保存运行元数据，包括代码提交标识、模型名称、套件版本、scope 快照、超时与 token 预算。缺少其中任何一项，不同日期的两个数字就可能没有可比性。逐 Finding 结果应包含去重指纹和 TP/FP/FN 判定理由，汇总报告只是它们的可读视图。

命令接口可以保持简单，但“可执行”不等于“已经完成真实评测”：

```bash
python bench/run_benchmark.py --suite xbow --output bench/results/xbow.md
python bench/run_benchmark.py --suite vuln-tf --output bench/results/vuln-tf.md
```

当前仓库中的运行脚本仍是占位骨架。它定义了结果结构和报告格式，但尚未接入 XBOW 部署、动态云场景及真实 Agent 执行。因此自动化建设的下一步，是把每个待实现分支替换为可离线复核的适配器，并用 fake executor 在 CI 中验证计分逻辑；真实靶场运行始终留在授权环境中。

## 五、防止“跑分幻觉”的三道约束

第一道约束是 ground truth。每个漏洞必须有稳定 ID、类型、位置和预期证据，安全对照项也必须显式登记。修改题目要升级套件版本，不能在成绩不理想时静默调整答案。

第二道约束是发现与验证分离。Cain 的 discovery executor 和 validation executor 使用独立会话，验证者只接收结构化 Finding 和证据，不继承发现者的推理上下文。这样能降低确认偏误，但不能保证模型永不犯错，所以最终仍要由确定性的匹配规则收口。

第三道约束是结果状态完整。系统错误、超时、待校验和预算截断都必须出现于报告。删除失败轮次再计算平均值，会制造一种虚假的稳定性；正确做法是保留全部运行，并同时展示成功率和四项核心指标。

## 六、七朵云的当前数据：覆盖快照不等于实测成绩

项目目标覆盖 AWS、Azure、GCP、阿里云、腾讯云、华为云和 Kubernetes 七类云环境。不过截至本文对应的仓库版本，只有阿里云 vuln-tf 已有可静态校验的 OSS 与 RAM 场景；XBOW 和动态云跑分适配仍未完成。因此不能诚实地发布“七朵云检出率”百分比。

|---|---|---|
| AWS | 检测模块已规划纳入统一套件，ground truth 待建设 | 未测量 |
| Azure | 检测模块已规划纳入统一套件，ground truth 待建设 | 未测量 |
| GCP | 检测模块已规划纳入统一套件，ground truth 待建设 | 未测量 |

| 腾讯云 | 检测能力已有代码测试，动态靶场 ground truth 待建设 | 未测量 |
| 华为云 | 检测模块已规划纳入统一套件，ground truth 待建设 | 未测量 |

这张表看起来不如一组漂亮百分比，但它更有价值：读者可以清楚区分“代码存在”“静态回归存在”和“动态实测完成”。首轮可信数据发布至少要满足三个条件：固定七类套件版本，保存逐条 ground truth 对齐结果，公开失败轮次与运行预算。条件未满足之前，零场景占位输出也不能被包装成 0% 或 100%。

## 七、总结与下一步：从一次跑分到持续回归

Benchmark 真正的用途是比较版本。每个版本跑本地合成场景，每个里程碑跑公开 XBOW 套件；同一模型、预算和套件下观察检出率、误报率、耗时与 token 趋势。如果检出率上升但 token 翻倍，或者平均耗时下降却出现更多预算截断，就不能简单宣布“性能提升”。

未来七朵云的结果应按平台、漏洞类型和场景难度拆分，而不是只给一个总分。总分会掩盖能力空洞：Agent 可能在对象存储配置上表现稳定，却完全漏掉 IAM 提权路径。分层数据才能指导技能、提示词、验证规则和工具链的具体改进。

可审计的评测不会消灭 AI 幻觉，但能让幻觉留下记录、进入统计并触发回归。对安全产品来说，这比一句“模型更强了”更重要。可信度不是模型自我声明出来的，而是由固定靶场、清晰口径、独立验证和不粉饰的结果共同建立。
