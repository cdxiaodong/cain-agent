# 标题候选（发布时择一）

1. **从单 Agent 到多 Agent 编排：AI 渗透测试 Agent 的架构演进**
2. **让中心编排、交叉验证和语义记忆约束 AI 渗透测试**
3. **AI 渗透测试的多 Agent 边界：什么时候该并行，什么时候该收口**

---

> 本文讨论授权测试系统的架构设计，不包含真实目标、真实凭证或未公开漏洞细节。Cain 仅供获得书面授权的安全测试使用。

## 一、单 Agent 的瓶颈不在智力，而在状态

一个 AI 渗透测试 Agent 最自然的形态是单会话：给它目标、授权范围和一组工具，让它从侦察一路做到报告。这个形态在早期很好用，链路短、调试简单、上下文看起来也完整。

但当目标变大，问题会依次出现。

第一是上下文污染。侦察产物、HTTP 响应、云资源配置、临时假设和已验证事实都堆在同一个对话窗口里，模型必须同时记住“已经确认的事实”“只是怀疑的方向”和“已经排除的路径”。窗口越长，早期证据越容易被后续叙述稀释，最终报告也就更难解释某条结论到底依据了哪一段请求。

第二是确认偏误。发现者和复核者如果是同一个会话，复核时天然带着自己的旧判断。它不是刻意作弊，而是概率模型在共享上下文下的常见倾向：前面已经写了“疑似 SQL 注入”，后面就更容易把普通错误页解释成佐证。

第三是失败传播。单 Agent 的路径是串行的，一次解析失败、一次超时或一次工具输出不合规，都可能让后续计划偏离原目标。工程师能靠重试缓解，但如果没有结构化失败分类，重试只是把同样的提示词再发一遍。

第四是成本失控。上下文越长，每次调用的输入都更贵；而其中很多内容对当前子任务并没有帮助。安全测试不是聊天，盲目把所有历史都塞给模型，既降低稳定性，也放大预算风险。

所以，从单 Agent 走向多 Agent，不是为了显得架构复杂，而是把不同信任级别的状态拆开：谁负责规划，谁负责执行，谁负责复核，谁负责记住可检索的历史。中心问题从“模型是否更聪明”变成“系统能否在不确定中保持边界、证据和可审计性”。

## 二、先划硬边界：编排器不是另一个模型

Cain 的第一层演进是引入确定性 Orchestrator。阶段序列被硬编码为：

```text
recon -> test -> report
```

它不接受外部传入的任意阶段顺序。跳阶段、重复执行已完成阶段、请求未知阶段，都会被状态机拒绝。每个阶段结束后，当前阶段、完成列表、时间戳和产物路径写入 `state.json`。这样即使进程中断，后续也能判断流水线停在哪一步，以及每个结论引用了哪些落盘文件。

这个设计的取舍很明确：阶段流转、scope 校验、危险操作熔断和产物契约由代码决定；路径选择和证据解释交给 Agent。换言之，编排器不是更聪明的模型，而是把不该给模型自由度的地方拿走。

这在渗透测试场景尤其重要。授权范围来自配置，而不是模型的自律；工具调用前先经过 scope 守卫，越界请求在执行前被拒绝。多 Agent 数量增加后，这条规则也不改变：无论有多少个 Solver，它们看到的都是同一个授权边界。

中心编排还需要保留回退能力。当前可用的经典链路已经能完成三阶段执行和发现校验，多 Agent 全链路仍在接线中。架构目标不是一次性替换，而是当新编排不可用时退回已验证的单通道，避免工程复杂度反过来影响可用性。

## 三、黑板：让 Agent 协作，但不互相污染上下文

多 Agent 系统有两种常见协作方式：一种让 Agent 互相聊天，另一种让它们读写共享状态。Cain 选择后者的核心原因是，安全结论需要区分事实和假设。

Blackboard 将状态分成两类：

```text
Idea    = 待验证方向，可被推翻
Finding = 候选或已确认发现，必须携带证据
Context = 侦察与执行过程中的共享上下文
```

这种分离避免了最危险的状态混杂：一个未确认的猜测被后续 Solver 当作事实引用。Solver 可以发布 Idea，验证后再转成 Finding；Finding 进入验证池复核，只有达到共识才成为报告候选。

黑板也降低了通信耦合。Agent 不需要知道彼此的提示词和完整历史，只消费带来源和状态的结构化记录。这样的间接协作有代价：需要维护线程安全和记录生命周期；收益是边界清晰，任何一个 Solver 的失败输出都不容易扩散成全局事实。

## 四、验证池：用多数表决降低单点误判

单会话校验解决了“发现者不能自证”，但仍是一个校验者做最终判断。并行验证池把这一层扩展为多个独立校验会话。

```text
candidate finding
  -> verification session 1 -> confirmed / rejected / inconclusive
  -> verification session 2 -> confirmed / rejected / inconclusive
  -> verification session 3 -> confirmed / rejected / inconclusive
  -> majority reduction
```

VerificationPool 的表决规则有几个细节：

| 规则 | 设计意图 |
|---|---|
| 至少两个独立会话 | 防止同一个执行对象伪装成多方复核 |
| 多数按全体会话计算 | 会话失败不能把剩余失败票凑成拒绝多数 |
| 无多数为 contested | 有分歧就保持不确定，不强行二选一 |
| 同时确认与拒绝时标记分歧 | 把风险暴露给报告层，而不是隐藏 |
| 输出必须绑定 finding_id | 防止校验结果串到另一条发现 |

这套机制的价值不是保证投票永远正确，而是让错误更难单点放大。一个校验会话超时或输出格式不合法，会被记为 `inconclusive`；一个会话把别的 Finding 的结论返回，也不能通过 ID 校验。最终报告看到的不是一句“模型确认存在”，而是每个会话的投票、错误和共识状态。

成本是必须承认的：验证会话数量增加，token 和时间近似线性增加。因此验证池只应作用于去重后的候选 Finding，而不是所有原始输出。终态发现可以跳过重复校验，池异常时回退单会话校验，避免为了架构一致性让 Finding 漏检。

## 五、语义记忆：检索需要的历史，而不是复制全部历史

多 Agent 带来另一个问题：Solver 之间如何利用彼此的工作成果？最粗糙的做法是把黑板全量塞进每个提示词，但这会重新制造单 Agent 的上下文膨胀。

Cain 的 SemanticMemory 采用可检索记忆。Finding 和共享上下文在写入时生成向量，查询时按相似度取有限条结果，并附带分数、来源和时间。默认实现是本地确定性哈希嵌入，不引入外部向量服务；也保留了替换嵌入提供者的边界。

```python
records = memory.search(
    "login sql injection",
    top_k=5,
    min_score=0.2,
)
```

这里的关键是语义记忆的信任级别。相似历史只能作为旁证，帮助 Manager 排序、补充线索或提示“此前存在相近证据”，不能单独证明当前目标存在漏洞。检索结果必须携带来源和分数，否则一个模糊相似项会被包装成因果依据。

语义记忆还要处理陈旧问题。上下文键更新时会替换旧向量记录，避免同一个事实存在多个版本；但跨任务的长期记忆仍需要版本、目标和授权范围隔离。否则上一次测试中的普通错误页，可能污染下一次测试的解释。

## 六、Manager：聚合判断，而不是重新发明结论

当 Solver、验证池和语义记忆都存在后，系统还需要一个控制面把证据收口。Manager 的职责不是替代它们再判断一次漏洞，而是把同一 Finding 的多路信号组织成带置信度和依据链的结论。

一个概念化的聚合输入如下：

```python
conclusion = manager.aggregate(
    finding=primary_finding,
    verification=pool_report,
    memory_hits=semantic_search_results,
)
```

输出应包含四类信息：候选发现本身、验证共识、相似历史旁证和最终置信度。验证共识是主信号；语义记忆只能小幅上调或下调，不能把 rejected 变成 confirmed。若验证池分歧很大，即使记忆中有相似记录，结论也应保持 contested 或降低置信度。

依据链同样重要。报告阶段需要能回答：

1. 这条发现最初由哪个 Solver 提出；
2. 每个校验会话给出了什么状态；
3. 多数表决如何收口；
4. 检索到了哪些历史旁证；
5. 为什么最终置信度是这个区间。

这样，Manager 的“智能”被限制在解释证据关系上，结论边界仍由验证状态和规则表决定。它也不直接触碰目标系统，只做任务路由、状态汇总和资源调度。

需要说明的是，截至本文对应的 `main` 基线，Manager 判断聚合与多 Agent 全流程接线仍是并行推进中的工作，尚未合入。本文描述的是该控制面的目标契约，不把它写成已经可用的运行事实。

## 七、失败自愈与预算：多 Agent 不能无限重试

多 Agent 系统容易把失败藏进并发里。某个 Solver 连续空结果、解析失败或超时，如果没有中心监控，就会表现为整轮任务变慢、变贵，最后只得到一份模糊报告。

失败自愈的第一步是分类。空结果、解析失败和超时对应不同动作：解析失败可以收紧输出契约后重试；超时或目标过大应先分解；连续达到上限则跳过并记录原因。重写提示词不是让模型随意发挥，而是针对失败模式改变任务边界。

第二步是预算。每个阶段、每次重派和每个验证池都应有上限。多 Agent 的收益若来自更多调用，就必须在报告中同时呈现耗时和 token；否则只是把一次不确定判断拆成多次更贵的不确定判断。

第三步是保留失败状态。`system_error`、`inconclusive`、预算截断和跳过原因不能被悄悄删除。它们不是报表上的瑕疵，而是下次修复提示词、技能或验证规则的依据。

## 八、当前状态：架构能力与实测数据分开

为避免传播时夸大，当前能力应按下表区分：

| 能力 | 当前状态 | 效果数据 |
|---|---|---|
| 确定性三阶段编排 | 已在经典链路使用 | 端到端效果未在本文测量 |
| 独立验证池 | 已合入并接入校验流水线 | 误报率收益未测 |
| 语义记忆 | 已合入库和黑板检索 | token 节省未测 |
| 失败自愈 | 已有分类和重派机制 | 恢复成功率未测 |
| Manager 置信聚合 | 并行任务推进中，未合入 | 无实测数据 |
| 多 Agent 全流程 CLI 接线 | 并行任务推进中，未合入 | 无实测数据 |

这些“未测”不是缺陷，而是工程回归的必要边界。多 Agent 架构只有在同一目标、同一预算、同一 ground truth 下比较，才能说明检出率、误报率、耗时和 token 的真实变化。单元测试证明组件契约正确，不能替代真实授权靶场上的端到端评测。

## 九、总结：从更聪明的模型到更可信的系统

这轮架构演进的核心不是增加 Agent 数量，而是重新分配信任：

1. Orchestrator 管阶段纪律、授权边界和产物契约；
2. Solver 只在受限任务内执行路径探索；
3. VerificationPool 用独立会话和多数表决处理候选发现；
4. SemanticMemory 提供带分数和来源的历史旁证；
5. Manager 聚合依据链和置信度，不凭空制造结论。

多 Agent 也不是终态。如果某个任务只需要单会话就能稳定完成，额外的编排、表决和检索就是负资产。架构选择应由风险驱动：上下文越容易污染、结论越依赖证据、失败成本越高，越值得拆分控制面与执行面。

对 AI 渗透测试工具来说，可信度来自结构约束：发现者不自证，历史不自证，编排器不把安全边界交给概率，报告能回溯每条证据。多 Agent 让系统更有弹性，但这些硬边界才是它能被审计的前提。
