## 一、痛点:AI 渗透工具的"实战空位"

这两年 AI 渗透测试工具不少,但真正能拿去做授权评估的,一只手数得过来。绝大多数卡在同一个位置:**CTF 玩具化**。

它们的共同特征是:目标是一台静态靶机,要找的是一个预设好的 flag,环境里没有 WAF、没有风控、没有限流。跑出来的"漏洞"是语法模式匹配的结果——注入点长什么样,工具就报什么样。这跟真实企业内网差了十万八千里。

真实授权评估里,真正值钱的不是某个参数有没有单引号,而是:

- **业务逻辑缺陷**:越权、支付绕过、状态机篡改,这些靠正则扫不出来;
- **认证链攻击**:OAuth 重定向劫持、JWT 伪造、会话固定,需要理解多步骤上下文;
- **云配置错误**:IAM 过度授权、对象存储公开暴露、元数据端点 SSRF——这是过去三年云上事故的重灾区,而国内六大云厂商的安全检测工具近乎空白。

更关键的是:**谁来保证 AI 报的漏洞是真的?** 一个会"幻觉"的 Agent,把它放进授权评估交付物里,等于把责任风险也一起交付了。市面上几乎没有工具正面回答这个问题。

Cain 想填的正是这三块空位:业务逻辑漏洞、国产云安全检测、以及一个让 AI 自己校验自己的闭环。

## 二、差异化:不只是又一个 AI 调用 OpenAI 接口

Cain 的定位很明确:**首个懂国产云的实战型 AI 渗透工程师**。不是 CTF 靶场型,不是论文复现型。它有三个其他工具没有的差异化点。

**第一,国产云原生支持。** 现有的云安全 AI 工具清一色只认 AWS。但国内企业跑在阿里云、腾讯云、华为云上的资产,它们的 IAM 体系叫 RAM/CAM/IAM,API 不通、权限模型不一样、连命名前缀都不一样(阿里云 AK 前缀是 `LTAI`,AWS 是 `AKIA`)。Cain 的云模块已覆盖七大云厂商:阿里云(OSS 暴露检测 + RAM 提权路径分析)、AWS(S3 ACL + Policy + Public Access Block 全覆盖)、腾讯云 COS(ACL + Policy + 敏感文件扫描)、华为云 OBS(S3 兼容 API)、Azure Blob、GCP GCS。从阿里云起步走通了这条路,七厂商扩展已基本到位,后续补深度而非铺广度。

**第二,校验闭环——让 AI 自己查自己。** 这是 Cain 架构上最硬的设计。后面单独讲。

**第三,确定性工程框住智能体。** Cain 不把安全边界交给 AI 的"自律",而是用硬编码的工程约束。阶段流转、scope 强制、危险操作熔断,全是 Python 确定性逻辑;只有路径选择和证据分析交给 Agent。这个哲学贯穿始终。

## 三、架构:一图流

[图:架构 —— 编排循环 + 双 Agent 校验 + 安全 Hook 三层]

用文字描述这张图:

Cain 的核心是一条**确定性编排循环**:recon(侦察)→ test(测试)→ report(报告),阶段流转由 Python 状态机硬编码控制,不允许跳序。

循环内部有两层 Agent。**发现 Agent** 负责侦察和漏洞探测,把结果写成结构化的 Finding;**校验 Agent** 在报告生成前介入,用独立的会话(Session)逐条复核发现——同一个 Agent 不能既当运动员又当裁判,这是架构级的防自证约束。

整条循环被三道安全 Hook 包裹:

- **ScopeGuardHook**:从 scope.yaml 白名单构造,任何 Bash 命令提取出的目标不在白名单就阻断(deny 优先,默认拒绝);
- **CredRedactHook**:所有 Agent 输出落盘前强制脱敏,AccessKey、Token、私钥等凭证模式被替换为可审计的哈希格式,明文不进任何文件;
- **Token 预算熔断**:idle 超时和总墙钟预算双防线,到点优雅中断,不留半截炸裂的循环。

所有状态都走 **Workspace 外置记忆**:assets、findings、阶段状态全是文件,崩溃可恢复、全程可审计。

## 四、真实能力演示(合成示例数据)

下面用两个云模块的实际输出展示 Cain 的检测能力。数据全部来自自有账号内搭建的靶场,桶名和用户名已脱敏替换,不涉及任何真实目标。

### 场景一:OSS 对象存储暴露检测

Cain 的 OSS 暴露检测模块(`OssExposureChecker`)以只读方式检查桶的 ACL 和 Policy 配置。下面是对一个靶场靶标桶的检测结果(合成示例):

```
检测对象: example-bucket-assets
ACL 状态: public-read
定级:     high
判定依据: public-read = 任何人可读取桶内对象 = 数据暴露
```

对照桶的检测结果:

```
检测对象: example-bucket-private
ACL 状态: private
定级:     info
判定依据: private = 正确配置,非暴露
```

定级规则是**代码常量**,不是模型输出的"我觉得这个很严重":公开可写 = critical,公开读 = high,私有 = info。检测器只做事实判断,不做主观评分。

### 场景二:RAM 提权路径分析

Cain 的 RAM 提权分析模块(`RamPrivescAnalyzer`)以只读 Get/List API 枚举用户和角色的权限,然后匹配一组提权路径规则。下面是对靶场靶标用户的分析结果(合成示例):

```
分析对象: vuln-ram-user-demo
命中的提权路径:
  1. ram:AttachPolicyToSelf (critical)
     该用户持有 ram:AttachPolicyToUser 权限,可为自己挂载任意策略
  2. ram:CreateAccessKey-for-HighPriv (critical)
     该用户持有 ram:CreateAccessKey 权限,可为任意用户创建 AccessKey

对照用户: safe-ram-user-demo
命中的提权路径: 无(仅持有 OSS 只读权限,零 RAM 写权限)
```

规则表覆盖五类提权路径:借高权角色执行代码(PassRole)、自我挂策略(AttachPolicyToSelf)、为他人生成 AK(CreateAccessKey)、劫持控制台登录(LoginProfile)、角色链提权(AssumeRole)。每条规则标注最小权限集和严重等级——同样是代码常量,模型不能自行加码或降级。

## 五、工程哲学:用确定性框住智能体

这是 Cain 跟其他 AI 安全工具最大的分野。

大多数 AI 安全工具的思路是"给 AI 更多自由,让它更聪明"。Cain 反过来:**越是危险的边界,越要用硬编码约束,越不能交给 AI 自行判断**。

具体怎么框:

- **阶段不跳序**:recon 没完不能进 test,硬编码状态机,跳序直接抛异常;
- **scope 不可越**:白名单外的目标一律阻断,不是"请 AI 注意 scope",而是代码层面拒绝执行;
- **凭证不落盘**:Agent 的任何输出在写入 Workspace 前先过脱敏 Hook,即便 Agent 在输出里带回了目标系统的 AccessKey,落盘的也只是哈希;
- **发现需校验**:报告前每条发现由独立 Agent 复核,校验结果有四种状态(confirmed / false_positive / inconclusive / system_error),不通过校验的发现不会进最终交付物;
- **预算有上限**:idle 超时和总预算双熔断,到点就停。

这套约束的结果是:**Agent 越界的尝试在工程层就被挡住了**,而不是在"事后审计日志"里发现。安全从业者的责任风险因此大幅降低。

## 六、校验闭环详解:AI 怎么查自己

校验闭环是 Cain 架构里最值得单独说的设计,因为它直接回答了"AI 报的漏洞能信吗"。

流程是这样的:发现 Agent 把每条可疑发现写成结构化 Finding,初始状态是 `validation_inconclusive`(待校验)。报告生成前,校验流水线介入:

1. **去重**:四元组指纹(目标+漏洞类型+证据哈希+端口)归一化,同一条漏洞重复出现只留一条;
2. **逐条校验**:校验 Agent 用独立会话复核每条发现的证据,输出四状态判定;
3. **容错**:单条校验异常标 `system_error` 继续,不炸整条流水线;
4. **幂等**:已是终态(confirmed/false_positive)的发现重跑不重复校验。

关键约束:发现 Agent 和校验 Agent 不能是同一个对象/会话。校验 Agent 看到的证据包裹 `[UNTRUSTED_DATA]` 标记,提醒它这些数据来自不可信来源。模型的严重等级建议必须过规则表收口——模型说 critical 但规则表只到 high,最终就是 high。

这个设计让交付物里的每条发现都经过独立交叉验证,大幅降低幻觉漏洞进入报告的概率。
