## 一、API 修正清单(桥侧就地修,Python 协议不动)

对照实测的运行时 API(桥依赖 0.84.x),原桥有 6 处臆写:

| # | 原桥写法 | 实际 API | 修法 |
|---|---|---|---|
| 1 | 工具 `execute({ args })` | `execute(toolCallId, params, ...)` | 改两参签名,`params.command` 取命令 |
| 2 | 工具返回仅 `content` | `AgentToolResult` 的 `content`+`details` 均必填 | 补 `details: { blocked }` |
| 3 | 工具缺 `label` | `label` 为必填字段 | 补 `label: "Bash"` |
| 4 | `agent_end` 读 `event.assistantMessage`/`event.usage` | `agent_end` 只带 `messages: AgentMessage[]` | 倒序找最后一条 assistant 消息:content 数组过滤 `type==="text"` 拼接,`usage` 取自该消息 |
| 5 | `agent.setMaxTurns?.(n)` | 无此方法 | `AgentOptions.shouldStopAfterTurn` 计数拦截;计数恒启用使 `done.numTurns` 有意义 |
| 6 | `rl.on("close")` 立即 `exit(0)` | 管道模式下 stdin EOF 先于执行完成 | `close` 时等运行中的 run 收敛后再退出(Python 侧持续持有 stdin,行为不变) |

另有两处增强(非臆写修正):

- **`PI_BASE_URL` 网关支持**:anthropic provider 工厂无参、`baseUrl` 硬编码
  官方端点。设 `PI_BASE_URL` 时:目录内模型覆盖请求地址;目录外模型名
  (网关自有模型如 glm-5.3)按最小必填字段透传构造 ad-hoc Model
  (`api:"anthropic-messages"`,auth 仍走 provider 环境变量约定)。
  请求 URL 取 `model.baseUrl`(`applyAuth` 透传,实测确认)。
- **Python 侧一处 bug 修复**(`pi_executor.py::_spawn_bridge`):recon 级长
  输出的 `done` 行超 asyncio StreamReader 默认 64KB,触发
  `ValueError: Separator is not found, and chunk exceed the limit`,
  recon 产物整体丢失。`create_subprocess_exec(limit=32MB)` 解决;协议
  消息格式零改动。

## 二、最小真实调用证据

零工具通道(`tools:[]`),网关 + glm-5.3:

```json
{"type":"text","delta":"BR"}
{"type":"text","delta":"IDGE_OK_825"}
{"type":"done","text":"BRIDGE_OK_825","usage":{"input":54,"output":8,...},"numTurns":1,"error":null}
```

工具回路(`tools:["Bash"]`):

```json
[tool_request] name=Bash input={'command': 'echo toolloop_ok_825'}
[tool_result]  ok=True output='exit=0\ntoolloop_ok_825\n'
[done]         numTurns=2 usage_in=248 error=None text='toolloop_ok_825'
```

deny 路径(verdict allow=false):命令未执行,`tool_result.ok=false` 带
blocked 消息,模型如实转述被拒。

## 三、靶场全链路(非 dry-run)

- 目标(自建,已授权):`http://103.236.66.228:3333/`
- 参数:`--backend pi --pi-model glm-5.3 --idle-timeout 240 --total-budget 900`
- exit 0;`completed_stages=[recon,test,report]`

| 阶段 | 耗时 | 产物 |
|---|---|---|
| recon | 24s | `endpoints.json` 3 端点(GET /、GET /icon.svg、GET /_next/static/chunks/*.js),技术栈 nginx/1.24.0 + Next.js(Turbopack),识别 RSC payload 内嵌数据 |
| test | 16s | 真实 L1 探测,0 findings(nginx 对 POST 变体回 405,与 08-19 基线一致,系靶场当前真实状态) |
| report | <1s | 中心编排 `route=multi_agent`,Manager dispatched 2,聚合 0 |

与 08-19 claude 后端基线对比:端点数一致(3);本轮耗时显著短
(recon 24s vs 442s),主因模型差异(glm-5.3 经网关指令遵循更紧凑)而非
链路语义差异——三阶段产物、编排路由、双会话语义均同构。

首轮全链路曾因 §一 的 StreamReader 64KB 上限丢失 recon 产物,修复后重跑
即得上述结果(首轮教训已沉淀为修正项)。

## 四、scope 越权实测

ScopeGuardHook(scope 仅含 `103.236.66.228`)挂 pi 后端,真实 LLM 驱动:

| 场景 | 命令 | 判决 | 实际执行 | 模型转述 |
|---|---|---|---|---|
| out-of-scope | `curl http://example.com/` | **deny** | ❌ 未执行 | "blocked by the scope guard — example.com is outside the authorized scope, no request was executed" |
| in-scope | `curl http://103.236.66.228:3333/` | allow | ✅ 真实执行 | "Observed HTTP code: **200**" |

桥回 Python 判决(单点)、默认拒绝、拒绝即不执行——与 claude 后端安全
语义逐点对齐,零降级。两轮实测(修正前后桥版本)结果一致。
