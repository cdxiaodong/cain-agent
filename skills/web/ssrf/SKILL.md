# 服务端请求伪造测试技能（SSRF）

> 定位：面向**真实授权业务系统**的服务端出站请求验证。核心难点不是找到一个能请求外网的点，而是判断「能否触达内网敏感服务、能否读取云元数据端点换取实例凭证」——后者是与云模块呼应的关键链路，也是 SSRF 升级为 critical 的分水岭。

## 触发条件

满足以下任一信号即应进入本技能：

- 应用存在「由服务端发起对外请求」的功能：URL 预览/链接卡片生成、图片/头像代理下载、网页截图、PDF/Office 在线转换、RSS/Feed 订阅抓取、Webhook 出站测试、SSO/OAuth 回调、第三方 API 代理转发。
- 参数为 URL 或主机名形态：`url=` / `target=` / `image_url=` / `webhook_url=` / `src=` / `next=` / `redirect=` / `callback=`，且后端会基于该值发起 HTTP(S) 请求。
- 文件导入类功能：远程 URL 导入（如「从 URL 导入图片/文档」）、XML/CSV 远程加载——XXE 与 SSRF 常伴生，`file://` / `gopher://` / `dict://` 协议是否被支持是高价值信号。
- 响应能反映目标可达性：错误信息泄露内部 IP/端口、连接超时与拒绝连接的差异、返回内容包含目标页面的特征（标题、状态码、响应头）。
- 云环境特征：目标部署在云上（侦察阶段 `assets.json` 记录了云厂商指纹），SSRF 可达元数据端点即可换得实例角色凭证——这是 SSRF 影响放大的决定性因素。

## 三层测试模型

> 对齐 DESIGN §3.1。SSRF 的 L1/L2/L3 划分核心是「请求是否真由服务端发出」与「能否触达内网/元数据」，而非 payload 多寡。

### L1 探测

目标：确认服务端确实基于用户输入发起出站请求，并定位可控点，不急于打内网。

- DNS 回连确认：传一个指向自有受控 DNS 服务器的域名（如 `cain-ssrf.<collab-id>.burpcollaborator.net` 或自有 DNSLOG），在 DNS 日志观测是否收到来自目标服务端出口 IP 的解析请求——这是「服务端发起了请求」的最强旁证。
- 协议支持探测：依次尝试 `http://` / `https://` / `file://` / `gopher://` / `dict://` / `ftp://`，记录哪些协议被接受（基于响应错误差异判断，而非盲目发包）；`file://` 可读本地文件、`gopher://` 可打内网任意 TCP 协议，是高危能力。
- 端口与主机反馈：传 `http://127.0.0.1:22` / `:80` / `:3306` / `:6379` 等，观察连接拒绝（端口关闭）与连接成功/超时（端口开放）的响应差异——这构成内网端口扫描能力，但须克制请求量、不做全端口扫描。

### L2 验证

目标：证明 SSRF 能触达**有价值的内网/外部目标**，并产出可复现证据。

- 内网可达性验证：传内网网段常见地址（`127.0.0.1` / `localhost` / `10.0.0.*` / `192.168.*` / `172.16-31.*` / 容器网络 `169.254.*`），用响应差异或回连确认服务端能访问内网——注意 scope 约束，内网探测以「证明可达」为限，不做横向资产枚举。
- 元数据端点探测（与云模块呼应，SSRF 升级 critical 的关键）：
  - AWS / 通用 IMDSv1：`http://169.254.169.254/latest/meta-data/` 及 `/iam/security-credentials/<role-name>` —— 若能返回临时 AccessKey/Token 即证明可窃取实例角色凭证。
  - 阿里云：`http://100.100.100.200/latest/meta-data/` 及 `.../ram/security-credentials/<role-name>` —— 国产云独有地址，是本项目差异化的体现。
  - GCP：`http://metadata.google.internal/computeMetadata/v1/`（需带 `Metadata-Flavor: Google` 头，SSRF 若支持自定义头才可达）。
  - Azure：`http://169.254.169.254/metadata/instance?api-version=2021-02-01`（同样需 `Metadata: true` 头）。
  - 验证标准：能返回元数据内容（实例 ID、角色名、临时凭证）才算确认；仅能解析该地址不等于能取到凭证（IMDSv2 需先拿 token）。
- 盲 SSRF 证据建设：若响应不回显目标内容，依靠 OOB（DNSLOG / 受控 HTTP 回调）确认触达——为内网 IP 也能触发回连（通过 DNS rebinding 或可控子域名解析到内网 IP），证明盲 SSRF 同样可探内网。

### L3 绕过

目标：在存在 URL 校验、内网黑名单、协议白名单时证明 SSRF 仍可达。

- IP 表示变形：`127.0.0.1` 的等价写法（`2130706433` 十进制、`0x7f000001` 十六进制、`0177.0.0.1` 八进制、`127.1` 短格式、`[::1]` IPv6）绕过基于字符串匹配的黑名单。
- DNS rebinding：用极短 TTL 的自有域名，解析阶段返回合法外网 IP 通过校验、实际请求阶段返回内网 IP——绕过「先校验后请求」型防护。
- 重定向链：传入指向自有服务器的 URL，该服务器返回 `302 Location: http://169.254.169.254/...`，利用服务端跟随重定向绕过对初始 URL 的校验。
- URL 解析差异：利用解析器不一致（`http://evil@169.254.169.254/`、`http://169.254.169.254#@evil.com/`）骗过校验层但请求层访问元数据端点——以目标实际使用的库的已知解析差异为线索。
- 协议升级：若 `http://` 被允许但限制主机，结合 `gopher://` 或重定向构造内网 Redis/Memcached/MySQL 协议包，证明可达其他内网服务（克制使用，不造成实际写入）。

## 证据要求

什么才算确认 SSRF（禁止仅凭「服务端请求了外网」下结论，要证明触达了有价值目标）：

1. **服务端发起确认**：用 DNS 回连或受控 HTTP 回调，留下「目标出口 IP 发起的解析/连接」日志作为服务端行为的硬证据。
2. **触达有价值目标**：至少证明以下之一——内网服务可达（含端口/服务指纹）、云元数据端点可达并返回了实例信息或凭证、内部管理接口可达；只打了一个外网 benign 站点不算漏洞确认。
3. **元数据证据特别要求**：若涉及元数据端点，证据记录「能取到什么」（实例 ID / 角色名 / 是否含临时凭证），但**临时凭证原文绝不落盘、不落明文**，只记录「凭证存在 + 哈希」。
4. **PoC 可复现**：提供完整触发请求（URL 参数、method、body 脱敏）与「如何观测到触达」的步骤（看哪条回连日志、响应差异在哪）。
5. **影响说明**：注明该 SSRF 的边界——能否读元数据换凭证、能否探内网端口、能否打非 HTTP 协议——基于已验证能力而非假设。

## 禁止事项

- **仅授权目标**：SSRF 极易触达 scope 外资产，所有探测目标（含内网 IP、元数据端点）必须在书面授权范围内；scope 外的内网段一律不探。
- **不窃取/滥用云凭证**：即使 SSRF 能取到实例角色临时凭证，**只记录「凭证存在 + 类型 + 哈希」证明漏洞成立，绝不下载、保存、使用该凭证去操作云资源**——证明可窃取已足够定级，使用即越界。
- **不破坏内网服务**：触达内网 Redis/MySQL 等服务时只做「可达性 + 指纹」探测，不执行写入/删除/修改类命令；通过 gopher 构造的协议包不得包含持久化或破坏性操作。
- **凭证不落明文**：探测过程中任何位置出现的 AK/SK/Token/连接串，证据与日志只存哈希。
- **不做全端口/全网段扫描**：内网探测以「证明 SSRF 可达内网」的最小请求量为限，不做 65535 端口全扫或 /16 网段枚举——既无必要又违反最小影响原则。
